# DevDocQA 优化清单

每次改动新增一条记录，写清为什么做、怎么做、功能体现、源码和验证。实测时标明环境、样本和指标口径。

## 01 问答与文档入库的调度隔离 · 2026-11-24

- **为什么做**　入库和问答原先共用 FIFO、执行名额和等待容量。批量入库时，已有资料的问答也会跟着排队。
- **怎么做**　按任务类型分别管理 FIFO、在途执行数和已预留名额。提交、数据库恢复和终态后释放名额都走对应队列。恢复查询返回后重新判断重复和剩余容量，再按实际可入队的任务占位，减少查询期间误报队列满。问答沿用 `AI_CONCURRENCY` 和 `QUEUE_CAPACITY`，入库新增 `INGEST_CONCURRENCY` 和 `INGEST_QUEUE_CAPACITY`。默认问答 1 个执行名额、16 个等待名额，入库 1 个执行名额、4 个等待名额。
- **功能体现**　批量上传期间可同时提交针对已就绪资料的问答。`GET /health` 的 `scheduler.question` 与 `scheduler.ingest` 分别返回 `active`、`queued`、`reserved`，可以观察两类任务是否同时推进。两类任务仍访问同一个 Worker、模型服务和数据库。
- **源码**　[队列状态结构](../backend/src/server.cpp#L234) · [入库入口](../backend/src/server.cpp#L328) · [问答入口](../backend/src/server.cpp#L496) · [调度](../backend/src/server.cpp#L532) · [终态写库与归还](../backend/src/server.cpp#L595) · [按类型恢复排队任务](../backend/src/server.cpp#L646) · [配置](../backend/include/docqa/core.hpp#L121) · [混合负载脚本](../scripts/benchmark.py#L44)。
- **验证**　Clang Release 完整构建，C++ 核心测试 1/1 通过，Worker 49 项通过、1 项跳过。原生接口回归包含缓存、限流、截止时间，以及重启后问答和入库两类排队任务均恢复。基线与当前版均删除了文件名校验前误留的 `disk_`，恢复编译后再比较。[文件名校验](../backend/src/server.cpp#L112) · [原生接口回归](../reports/optimization-2026-11-24/native-integration.json)

  混合负载对照使用原生 C++ 服务、PostgreSQL/pgvector、fakeredis TCP 替身。两个版本总执行名额均为 2、总等待容量均为 16。基线共享名额，优化版各类型各用 1 个执行名额、8 个等待名额。每组 6 个入库、2 个问答，共 5 组。测试在入库请求注入 800 ms 延迟，模拟生成延迟 150 ms。两个版本均成功 30 个入库和 10 个问答。

  | 混合负载指标 | 共享队列 | 分开调度 |
  | --- | ---: | ---: |
  | 问答完成 P50 | 2,770.9 ms | 304.5 ms |
  | 问答完成 P95 | 2,783.9 ms | 405.1 ms |
  | 入库吞吐 | 2.292 份/秒 | 1.184 份/秒 |

  这组负载下问答 P95 降低 85.4%，入库吞吐下降 48.3%。原先入库可占两个执行名额，分开后只能占其中一个。该结果描述模拟负载下的取舍，真实模型的两类任务仍争用相同的模型和硬件资源。[逐组压测结果](../reports/optimization-2026-11-24/mixed-scheduling.json)

## 02 记录实际入模证据 · 2026-11-24

- **为什么做**　召回前 5 条只是候选。有些片段会因提示词字节预算被裁掉，仅查看候选和最终引用，难以判断正确证据漏在哪一步。
- **怎么做**　记录实际保留的编号、被裁掉的编号和原因、消息正文字节数及预算、模型原始声明的引用编号。模型输出的 JSON Schema 不接收追踪字段，追踪由 Worker 填写。精确缓存键更换命名版本，避免旧缓存命中时缺失追踪。
- **功能体现**　真实模型成功任务的 `GET /v1/jobs/{id}` 返回 `result.evidence_trace`，可与 `retrieval` 和 `citations` 对照。Mock 或未调用生成模型的情况，追踪为 `null`。追踪不用额外保存完整提示词。
- **源码**　[提示词裁剪](../worker/app/providers.py#L33) · [追踪生成](../worker/app/providers.py#L172) · [追踪字段](../worker/app/models.py#L36) · [结果组装](../worker/app/main.py#L108) · [缓存版本](../backend/include/docqa/core.hpp#L77)。
- **验证**　Worker 单元测试截获实际发送的 JSON，核对保留编号、删除编号和消息字节数。真实模型测试集的 35 个成功结果都有追踪。最终构建已复跑单文档真实模型冒烟，通过了公开接口的追踪检查。Q045 的模型声明编号是 `[1, 2]`，正文把第二个编号写作 `[2]`，最终引用只有 `[S1]`，可以定位到生成格式与引用筛选之间。开发集成功且有参考文档的 15 题上，分别模拟现有尾部裁剪和逐条跳过放不下的片段，两者保留的编号逐题一致，文档命中都是 15/15，因此本轮保留原裁剪策略。[追踪回归测试](../worker/tests/test_providers.py#L148) · [开发集裁剪对照](../reports/optimization-2026-11-24/prompt-budget-dev.json)

## 03 真实模型评测与改进基线 · 2026-11-24

- **为什么做**　一次真实模型冒烟能说明单条链路可运行。需要固定语料和题集，才能比较召回、证据裁剪、生成和失败分布。
- **怎么做**　沿用 30 篇语料、开发集 20 题和测试集 40 题。评测只向本次已入库的语料提问，每题落盘，分别记录候选文档命中、入模文档命中和任务失败。答案正确性与引用支持性按参考答案和引用原文复核。
- **功能体现**　`evaluate.py` 输出逐题报告，`score_report.py` 显示已记录题数、成功、失败以及每项指标的有效样本数。两个文档命中指标均以参考文档为单位，回答和引用质量单独评分。
- **源码**　[逐题检查点](../scripts/evaluate.py#L15) · [命中计算](../scripts/evaluate.py#L68) · [评分汇总](../scripts/score_report.py#L7) · [题集](../learning/eval/questions.jsonl) · [复现方法](evaluation.md)。
- **验证**　使用本机 Ollama（BGE-M3 嵌入、Qwen3 4B 生成）、原生 PostgreSQL/pgvector、Redis TCP 测试替身。现版开发集完成 20 题，18 题任务成功，2 题失败。带追踪的新版测试 40 题，35 题返回结果，5 题返回 `worker_failed`。此轮 40 题在修正恢复查询临时占位前执行，后续改动限于 C++ 恢复路径。开发集和测试集题目不同，分数用于定位问题和建立基线。

  | 测试集指标 | 实测 |
  | --- | ---: |
  | 成功且有参考文档的题，前 5 条覆盖全部参考文档 | 27/28（96.4%） |
  | 同一批题，实际入模片段覆盖全部参考文档 | 27/28（96.4%） |
  | 成功任务中，逐题复核答案正确 | 20/35（57.1%） |
  | 全部 40 题中，成功返回且答案正确 | 20/40（50.0%） |
  | 成功且可回答的题，最终引文支持答复 | 15/28（53.6%） |
  | 无答案题，`insufficient_evidence` 为真 | 6/7（85.7%） |
  | 无答案题，实际答复明确表达资料不足 | 5/7（71.4%） |

  逐题复核由 Codex 按参考答案和引用原文完成，未经过第二人复核。Q034 前后给出了相反的关闭通知顺序。Q060 虽标记资料不足，答复只是复述问题。失败的 5 题没有回答可评分，公共接口中的 `worker_failed` 也无法区分其内部失败原因。[评测汇总与逐题复核](../reports/optimization-2026-11-24/evaluation-summary.json)
